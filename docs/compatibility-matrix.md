# Cross-Agent Compatibility Matrix

Last reviewed: 2026-08-21

This matrix records only official documentation claims from `docs/official-sources.json`. If a feature is absent from official docs, write `not documented` instead of inferring support.

Two rows are **non-vendor** and flagged as such: **Kuma Studio** (private runtime policy) and **gajae-code** (`gjc`, a community/MIT beta by Yeachan-Heo — its GitHub README is the only source, not vendor docs; claims below verified against the README on 2026-07-20). Do not read these two rows as official vendor guarantees.

For per-runtime **CLI spawn (interactive vs headless launch)** and resume invocation syntax, see `docs/cli-invocation.md`. The **Session Resume** table below owns the deeper resume semantics (session store, id form, capture timing).

## Skill Invocation

How a *typed* command reaches a skill differs per runtime — the explicit-invocation token is **not** portable, even where the `SKILL.md` format is. Do not assume `/<skill-name>` works everywhere.

| Platform | Explicit (user-typed) invocation | Model-triggered invocation | Source (verified 2026-06-22) |
|---|---|---|---|
| Claude Code | `/<skill-name>` — "You can type `/skill-name` to invoke it directly." Custom commands are merged into skills (`.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`). | Claude loads a skill automatically when relevant. `disable-model-invocation: true` restricts a skill to user-only invocation (removes it from Claude's context and from subagent preloading). | https://code.claude.com/docs/en/skills (verified 2026-06-22) |
| OpenAI Codex | `/skills` opens the skill selector; `$<skill-name>` mentions a skill in the prompt ("run `/skills` or type `$` to mention a skill"). Typing `/<skill-name>` is **not** a documented invocation form. | "Codex can choose a skill when your task matches the skill `description`." Disable with `allow_implicit_invocation: false` in the skill's `agents/openai.yaml`. | https://learn.chatgpt.com/docs/build-skills |
| Grok / xAI | "User-invocable skills also appear as slash commands, for example `/<skill-name>`." | Automatic invocation mechanics are not detailed in the cited page; discovery and slash invocation are. | https://docs.x.ai/build/features/skills-plugins-marketplaces |
| Hermes Agent | not documented in the cited source set | Skills and skill preloading are documented; trigger mechanics not detailed. | https://hermes-agent.nousresearch.com/docs |
| Antigravity CLI | A registered skill auto-converts to a typed `/<skill-name>` slash command in the TUI ("the skill is compiled, and `/format-tests` becomes available"). | Skills are compiled from `.agents/skills/` (workspace) and `~/.gemini/antigravity-cli/skills/` (global) on launch; per-skill model-trigger toggles are not documented. | https://antigravity.google/docs/cli/plugins |
| Cursor CLI | Type `/` in Agent chat and search for the skill name. | Cursor automatically discovers skills from skill directories and the agent applies relevant ones. `disable-model-invocation: true` makes a skill explicit-only. | https://cursor.com/docs/skills |
| gajae-code (`gjc`, community) | `/skill:<name>` (colon form, e.g. `/skill:deep-interview`) — **not** `/<skill-name>`. List/read out of session with `gjc skills list` / `gjc skills read <name>`. | Not documented in the README; default skills are bundled but per-skill model-trigger toggles are not described. | https://github.com/Yeachan-Heo/gajae-code (README, verified 2026-07-20) |

Implementer note: a cross-engine "typed command" surface therefore cannot standardize on one token. Ship the capability as a skill with strong trigger terms in `description` (works everywhere via model-triggering), and treat `/name` (Claude/Grok) vs `$name` (Codex) as per-engine sugar. Do not re-implement a slash parser in a host GUI/terminal layer above the engines to paper over this — see SKILL.md → Core Rules.

## Session Resume

Same-platform resume (continue an existing conversation on the same engine, by session id) is officially documented for all four primary worker runtimes. Cross-engine moves are a separate concern and out of scope here.

Notes for implementers:

- The resume **locator** (session/thread id) plus the engine's resume invocation is the minimum needed to continue same-platform. Capture the locator before the worker exits, keyed by cwd (the most stable cross-engine signal exposed here).
- Claude resume-by-id resolves **across projects**: passing a session ID searches the current project directory and its git worktrees first, then every other project on this machine (v2.1.223+). The cross-project search resolves the ID only when exactly one other project holds a transcript with messages for it, so a hand-copied duplicate reports not-found rather than resuming an arbitrary copy.
- Codex workers launched through the desktop **app-server** (`codex app-server --listen stdio://`) resume via `thread/resume`, not a CLI flag. The rollout JSONL **directory** is still not normatively stated in any Codex doc (the CLI reference dropped `~/.codex/sessions/` 2026-07-04; it survives only in a user-example prompt on the automations page) — verify the live rollout path before relying on a file-level integration. The history file `~/.codex/history.jsonl` is documented on the config-advanced page (as of 2026-07-05), but it is the transcript/history store, not the rollout directory.
- Hermes resume reads from `state.db` (SQLite), so a file-scan over `~/.hermes/sessions/` will not find resumable state — query the db (or the displayed "Resume this session with: hermes --resume <id>" line) instead.
- When a runtime does not document a resume capability, record `not documented` and require live verification before shipping.

## Project Instruction File Loading

The project-instruction *filenames* per engine are in the master table above; this section is the **loading mechanics** — how each engine discovers, merges, and times those files. Two axes matter and the engines diverge on both: (a) **ancestor walk-up** — does it climb from cwd toward the repo/filesystem root and merge every file it passes, or read only one? (b) **subdirectory (below-cwd) discovery** — does it pick up nested instruction files in child directories at all, and if so **upfront at launch** (always in context) or **on-demand** (only when the agent touches a file there)?

Key contrasts for implementers:

- **Subdir support is not the same as subdir timing.** Claude Code and Hermes load nested files **on-demand** (only when the agent touches that directory), while Gemini/Antigravity concatenates the whole subtree and **sends it with every prompt** (always in context — the doc doesn't label the scan lazy vs eager, but it is never on-demand like Claude). Same feature, opposite cost profile: Gemini pays tokens for the entire tree every prompt; Claude/Hermes pay only for directories in play.
- **Codex has no subdir lookahead at all.** It stops at cwd and walks *root → down*, so a `AGENTS.md` deeper than your cwd is never seen. Put module-specific guidance at or above cwd, and remember the 32 KiB combined cap silently truncates a long chain.
- **Hermes is first-match on the *type*, but it now merges within it.** A repo with both `AGENTS.md` and `CLAUDE.md` still feeds Hermes only `AGENTS.md` (it wins the precedence) unless `.hermes.md`/`HERMES.md` exists — so cross-engine repos relying on a `CLAUDE.md`-imports-`AGENTS.md` split must keep the canonical content in the file Hermes actually picks. What changed is what happens *after* that pick: inside a git repo Hermes concatenates the whole git-root-to-cwd `AGENTS.md` chain, so it now behaves like Codex on the ancestor axis rather than loading one file. The earlier "single file, no merge" reading is retired.
- **"Closer wins" direction is consistent but the walk direction is not.** Claude climbs cwd → root; Codex descends root → cwd; both end with the file nearest cwd taking priority (read last). The user-visible rule ("the instruction nearest where you launched wins") holds across both, but the set of files reached differs because Codex never goes below cwd and Claude lazy-loads what's below.
- For undocumented engines (Cursor tree-walk, Grok merge semantics) record `not documented`/`unknown` and require live verification before shipping behavior that depends on ancestor or nested discovery.
